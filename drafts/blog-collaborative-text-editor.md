Every piece of prose in Macro, whether it is a document, a task description, a meeting note, or the instruction file an agent reads before acting, goes through one text editor. We built that editor ourselves: Lexical for the editing surface, Loro CRDTs for convergence, and a sync server of roughly four thousand lines of Rust compiled to WebAssembly, running on Cloudflare Durable Objects with one object per document. All of it is open source in [our monorepo](https://github.com/macro-inc/macro), under AGPL, and this account links to the code wherever the code can speak for itself.

It took about two years to get from markdown files in S3 to the system we run now, and the route passed through a storage migration, a disconnect bug that resisted diagnosis for months, and one data-loss incident we would prefer never to repeat. The parts that transfer to other people's systems, about persistence ordering, about reconnection, about where the boundary of a collaborative document should sit, are the reason to write any of this down.

## why not tiptap

Collaborative editing is a solved problem if your requirements are ordinary. Tiptap wraps ProseMirror well, ProseMirror plus Yjs plus a hosted backend is a beaten path, and Liveblocks will sell you the whole thing as a service. We looked at all of them, and the reason none of them fit is that in Macro the editor is not a feature so much as a substrate: the same markdown surface is a standalone document, a task description, a channel draft, a comment, and the instruction set for an AI agent, which means one node schema, one mention system, and one permission model have to hold across all of those, including custom inline nodes that reference users, contacts, companies, dates, and other documents with live previews. Every off-the-shelf editor lets you add custom nodes; none of them expects your custom nodes to be the point.

The second misfit was server-side. Our backend has to read documents too, for search indexing, for export, and for feeding context to agents, and with a third-party collaboration cloud your server's view of a document is whatever their API returns. We instead run the same editor headless in a Cloudflare Worker and let the Rust backend call it over HTTP, so there is exactly one implementation of what a document means. The third was permissions: document access in Macro flows from the same system that governs email, channels, and CRM records, and our sync server enforces access levels per WebSocket message, dropping an edit that arrives on a viewer token at the server rather than trusting the client. You can wire that into someone else's collaboration service, but then you maintain a mapping between two permission systems for the life of the product.

<guess>There was also a less rational reason. An early prototype on a popular editor framework collapsed under the weight of our custom node types, with every minor upgrade breaking serialization in some new way, and within a month we were patching internals. Maintaining a fork of someone else's editor with none of the control is the worst quadrant to occupy, and we had been in it.</guess>

We chose Lexical, currently 0.32.1, for reasons that have mostly held. Headless operation is first class in `@lexical/headless`, which let us run the identical nodes and transformers server-side and ended up shaping the whole backend. The EditorState is an immutable, serializable tree snapshot produced on every update, which is the right input for a sync layer that works by diffing states. And Lexical has no opinion about collaboration beyond an optional Yjs binding, so building on Loro meant fighting fewer defaults than ProseMirror's collab module would have. We have complained about Lexical at length and at volume; <guess>it is a 0.x project that ships breaking changes casually, its reconciler has selection edge cases that surface only with IME and Safari, and its documentation assumes a comment box rather than a document system, so we carry a small pile of patches, and a rewrite onto ProseMirror gets proposed in anger about twice a quarter. We would still choose it, narrowly, because client-server parity through headless mode has been worth all of it, and because the node API has let a very small team maintain about thirty thousand lines of editor plugins without drowning. If Lexical lacked headless mode this would be a ProseMirror shop.</guess>

<guess>The CRDT evaluation, in early 2024, came down to Yjs, Automerge, and Loro. Yjs is the default and probably the safe choice. Loro won on three properties: it is Rust-native, so the browser (loro-crdt 1.5.9 via WASM) and our Rust sync server (the loro crate, 1.5.6) run the same implementation and cannot disagree about a merge; its movable list and tree support matched a block editor better than composing Yjs types; and its snapshot format, including shallow exports, gave us cheap semantics for handing a compact document to a newly connected client. Automerge we liked conceptually and benchmarked out on document size and import time as they stood at the time.</guess>

## the architecture

```
        browser (SolidJS)                    cloudflare                      backend (AWS)
┌──────────────────────────────┐  ┌──────────────────────────────┐  ┌──────────────────────┐
│ Lexical EditorState          │  │ sync-service (Rust → WASM)   │  │ documents service    │
│   ↕ serialize / reconcile    │  │ ┌──────────────────────────┐ │  │ (metadata, perms,    │
│ loro-mirror (state ↔ CRDT)   │  │ │ one Durable Object / doc │ │  │  JWT minting)        │
│   ↕ diff                     │  │ │  LoroDoc in memory       │ │  └──────────┬───────────┘
│ LoroDoc (loro-crdt, WASM)    │◄─┼►│  5s alarm: persist       │ │             │ initialize,
│   bebop over WebSocket       │ws│ │  op log in DO KV         │ │◄────────────┘ backfill
│ EphemeralStore (presence)    │  │ │  snapshots: DO SQLite    │ │  ┌──────────────────────┐
│                              │  │ │   (1.5MB chunks) → KV→R2 │ │  │ lexical-service      │
│                              │  │ └──────────────────────────┘ │  │ (headless Lexical,   │
│                              │  │  D1: peer → user mapping     │  │  md ⇄ loro snapshot) │
└──────────────────────────────┘  └──────────────────────────────┘  └──────────────────────┘
```

*Fig 2. The sync path. The editor never talks to the backend directly; the backend never parses a document itself.*

A client opens a WebSocket to `/document/:id/connect?token=<jwt>` and the Worker routes it to that document's Durable Object, created on demand, globally unique, holding the live `LoroDoc` in memory. The object answers with an initial sync containing a snapshot of the document and the current presence state, and from then on the conversation is eleven message types of [bebop](https://bebop.sh), a compact binary serialization:

```
// rust/sync-service/bebop/schema.bop (abridged)
union FromPeer   { PeerUpdate; PeerAwareness; PeerRequestSince;
                   PeerRequestSnapshot; PeerRegisterId }
union FromRemote { RemoteInitialSync; RemoteUpdate; RemoteAwareness;
                   RemoteSnapshot; RemoteUpdateAck; RemoteUpdateSince }
```

Local edits flow through a mirror layer that diffs the new editor state against the CRDT and emits minimal Loro operations; the Durable Object merges incoming updates into its in-memory document and broadcasts them to every other connection. Persistence is deliberately off the hot path. Each incoming update is appended immediately to an operation log in the object's key-value storage, and a five-second alarm acts as a debounced checkpoint that exports a fresh Loro snapshot, persists it, and clears the applied operations. Snapshots land in the object's attached SQLite, chunked at 1.5 MB per row to respect platform limits, with Workers KV and R2 behind it as fallback tiers.

The Durable Object model earns its keep here. A single-threaded actor per document, addressable from anywhere, with strongly consistent attached storage, is the shape of the collaborative-document problem, and we never wrote a line of room routing, locking, or leader election. The price is the lifecycle: Durable Objects evict their in-memory state after about ten seconds without messages, even while WebSockets are open, and importing a Loro snapshot is precisely the expensive operation we are trying to amortize. Our fix is the same five-second alarm that checkpoints state, doubling as a heartbeat that keeps the object warm while connections exist. It works, it costs almost nothing, and it has the characteristic smell of systems built on Cloudflare: an elegant platform primitive plus one trick to defeat its lifecycle policy.

Around the edges sit a small D1 table mapping Loro peer IDs to user IDs, populated when a client sends `PeerRegisterId`, which is how edits and cursors get attributed to humans, and a hook that notifies our search pipeline when a document's last peer disconnects, so re-indexing follows the end of an editing session rather than a cron schedule. The server lives in [`rust/sync-service`](https://github.com/macro-inc/macro/tree/main/rust/sync-service), the mirror in [`js/loro-mirror`](https://github.com/macro-inc/macro/tree/main/js/loro-mirror), the editor UI in [`js/app/packages/block-md`](https://github.com/macro-inc/macro/tree/main/js/app/packages/block-md), and the shared node and transformer definitions in [`js/lexical-core`](https://github.com/macro-inc/macro/tree/main/js/lexical-core).

## the shape of the document

The most contested design decision was the shape of the document inside the CRDT. The source of truth on the client is the Lexical EditorState, and we mirror it into a Loro document whose schema, defined in `js/lexical-core/markdown-loro-schema.ts`, is a recursive tree of CRDT containers: the root is a LoroMap, and every node is a map holding `$` (a LoroMap of metadata, including a stable node ID and the node type), `text` (a LoroText for leaf text, so concurrent edits within a paragraph merge at character granularity), and `children` (a LoroMovableList of child nodes). On every editor update the mirror diffs new state against old and emits operations; children are matched by stable node ID, and reorders are computed with a longest-increasing-subsequence pass so that dragging a block emits move operations on the movable list rather than delete-and-insert pairs, which is the difference between two people reordering the same list concurrently getting a sane merge and getting duplicated blocks.

<guess>Internally this whole approach went by the shorthand BFS, for the breadth-first way the reconciliation proceeds: diff the root's children, then each changed child's children, level by level down the tree. We argued about it for weeks at the start and we re-litigate it every time it hurts, because deep trees make worst-case diffs expensive and because moving a node between parents is the ugliest path in the mirror.</guess> The alternatives got serious consideration. A single LoroText holding the whole markdown string is beautifully simple and trivially compatible with every markdown tool in existence, but it makes structural edits into text merges, and two people each adding a row to the same table can converge on syntactically broken markdown; character-level semantics are the wrong granularity for block operations. A flat list of blocks with fractional ordering keys, the approach Figma popularized, handles reordering well but markdown is not flat, lists nest inside quotes inside lists, so you end up re-encoding the tree in parent pointers and reconstructing it on every read. <guess>Loro's native tree container exists for exactly this case, and the reason we composed maps, lists, and text ourselves is that when we started, the tree container was younger than the rest of the library and we could not convince ourselves of the cursor stability and ordering semantics, whereas behavior we assembled from primitives was behavior we could read. Given where Loro is today, this is the decision we would revisit first.</guess>

<guess>Whether the mirrored tree was right is a question we can answer with two years of incident history: the merge semantics have matched user intent, text merging like text and structure merging like structure, and the mirror gave us a clean seam between editor concerns and sync concerns, so Lexical has never had to learn anything about CRDTs. What we underestimated was how much of the system's total complexity budget the mirror itself would consume. It is the most subtle code in the stack, and nearly every collaborative bug we have shipped lived in the diff and reconcile layer rather than in Loro or in the server.</guess>

## from shared to collaborative

We did not start with CRDTs. <guess>For the first year documents were markdown strings stored as S3 objects behind our document storage service, DSS internally: online, shared, permissioned, and strictly single-player, with saves as whole-file writes on a debounce and concurrent editing "handled" by last-write-wins and a soft warning that someone else had the document open. For a small team dogfooding its own product this was tolerable for longer than we expected, and it let us build the editor experience, the nodes, mentions, and slash menu, before taking on any distributed-systems work. The sync service went up on Durable Objects in late 2024 and newly created documents got Loro state from day one while old documents stayed on S3, which was the right way to de-risk the new backend but meant every code path in the product grew a fork on the question of whether a given document was a sync document or a legacy one. The migration, early 2025, existed to delete that fork.</guess>

The migration era left fossils you can still read. There is a complete backfill orchestrator in [`markdown_backfill.rs`](https://github.com/macro-inc/macro/blob/main/rust/cloud-storage/documents/src/domain/markdown_backfill.rs) that walks legacy documents through a lifecycle: check whether the document already exists in the sync service, and if not, read the markdown from S3, convert it to a Loro snapshot by way of the headless editor, initialize the Durable Object, and flip a `ready / sync_service` flag in the database. It has dry-run states named `WouldInitialize` and `WouldUpdate`, an `--apply` flag, and a `--concurrency` option, because nobody runs a one-way migration over every user's documents at full speed on the first attempt. Our search pipeline still carries a comment reading "markdown parsing from DSS is deprecated" beside a fallback path for stragglers.

The reason to migrate at all, rather than letting old documents stay markdown-on-S3 indefinitely, was that the fork was the real cost: comments anchored to text ranges, mentions with live previews, version history, search, and AI reading your documents each had to be built twice or gated. <guess>The forcing function was comments. Anchoring a comment thread to a text range inside a file that is atomically replaced on every save is a losing game, and only the CRDT representation had the stable node identities and version history that anchoring needs. Once one load-bearing feature required the sync service, operating two document systems was strictly worse than one frightening migration.</guess>

## the disconnect bug

Every realtime system has a bug that becomes part of its personality, and ours was the disconnect bug. <guess>The symptom was a document going silently stale: no error, no broken UI, the editor apparently healthy while your edits quietly reached no one, usually after a laptop slept or a network blipped, and usually discovered minutes later when a colleague asked why the document hadn't changed. It survived roughly five months of being fixed, because it was not one bug but five or so root causes wearing the same symptom, and each fix was followed within days by a recurrence through a different hole.</guess>

It took so long partly because the failure modes are silent and partly because the cures interact. A WebSocket can be dead without either side knowing, which is just TCP, and the standard remedy is heartbeats, but heartbeats touch everything else in the system: <guess>our first heartbeat implementation killed connections during slow initial syncs, because importing a multi-megabyte snapshot on the main thread delayed the pong past the timeout, so the cure produced a new strain of the disease in which large documents disconnected more often than small ones.</guess> The scar tissue is still legible in the client, where the heartbeat is configured with `autoStart: false` next to a comment explaining that it must be started manually after the initial sync completes, precisely so that it cannot close the connection during a slow one (`js/app/packages/service-clients/service-sync/source.ts:96`). The second lesson was that reconnecting is not resuming. Early versions tried to resume the update stream across a gap, and every clever variant had a window in which an update broadcast during the disconnection was lost permanently, leaving a client connected, live, and missing one edit until the next full snapshot. The code that survived is deliberately unclever: on every reconnect the server sends a complete fresh snapshot and presence state, the client re-imports it wholesale, and CRDT idempotency makes re-applying anything already present a no-op. The client also re-mints its auth token on every reconnect, because long-lived tabs outlive JWTs, <guess>and an expired token on reconnect was, embarrassingly, one of the five root causes.</guess>

<guess>What ended the saga was instrumentation rather than insight. We put a visible connection status into the editor chrome, logged every state transition with its cause, and started treating stale-but-green as an incident, after which each remaining root cause was obvious the first time it fired. The conclusion we took is that in a distributed UI, observability of connection state is a product requirement rather than a debugging aid.</guess> The client now wears its paranoia openly: reconnection with a constant 500 ms backoff up to twenty retries, a ten-second heartbeat with a five-second timeout and two missed pongs tolerated, a heartbeat restart after every reconnect regardless of whether the sync succeeded, and a status pill that says you are disconnected instead of pretending otherwise.

## losing data

The disconnect bug was annoying; this one was frightening. <guess>For about two weeks in early 2025, a particular interleaving could eat edits. The Durable Object checkpoints by exporting a snapshot, persisting it, and then clearing the operation log it had applied, and under memory pressure an object could be evicted between accepting updates and the alarm firing, after which one recovery path read a snapshot staler than the operation log it had just been trimmed against. The document came back missing the last seconds of typing: silent, partial, and load-dependent, the worst possible combination. One of us watched half a paragraph of a design doc vanish on refresh in the middle of a meeting, and the particular feeling of an editor eating your words is one we now consider disqualifying for the product category. Feature work stopped for a week.</guess>

<guess>The fix came in layers, all still present in the code.</guess> Every incoming update is durably appended to the operation log, under an `o/` prefix with timestamp-ordered keys, the moment it arrives and before anything else touches it; a second append-only copy of every operation is kept under an `a/` prefix, an audit trail whose only job is to ensure no byte is ever unrecoverable; the version vector of the last exported snapshot is stored beside it so that a stale snapshot is detected rather than trusted; and internal `debug_dump_operations` endpoints exist so a human can exhume the raw operation log of any document. <guess>Replaying the audit log recovered everything that had been reported lost, which came to a handful of paragraphs across the team and, as far as we know, no customer documents.</guess> The durable lesson is that in a CRDT system, persistence ordering is the entire game: the mathematics guarantees that concurrent edits converge, and guarantees nothing about the order in which your storage layer commits writes. Treat the operation log as a write-ahead log, treat snapshots as an optimization, and never allow a checkpoint to delete the only copy of anything.

## one parser

The sync server does not understand documents. The Durable Object holds a `LoroDoc` and merges updates, but it has no concept of a heading, and semantic understanding lives in one place, which is Lexical, where Lexical does not mean the browser. The package `js/lexical-core` defines every node type and roughly 120 markdown transformers shared by client and server; [`js/lexical-service`](https://github.com/macro-inc/macro/tree/main/js/lexical-service) is a Cloudflare Worker running the editor headless, exposing markdown export, per-block text extraction for the search index, an AI-oriented rendering used to hand documents to agents, and a conversion from markdown to Loro snapshot bytes; and the Rust backend never parses markdown at all, calling the Worker over HTTP through `rust/cloud-storage/lexical_client` whenever it needs meaning. We accepted a network hop to avoid a second parser implementation, and the entire class of bug in which the backend renders a document slightly differently from the editor is structurally absent.

The artifact of this design we are fondest of is the blank document. A new empty document needs a valid Loro snapshot containing a root and one empty paragraph, and we did not want document creation to block on a Worker call, so the TypeScript build generates a canonical blank snapshot, `markdown-golden.1.bin`, which is compiled into the Rust binary with `include_bytes!`. Creating an empty document is a fire-and-forget write of a precompiled CRDT snapshot generated by the same editor code that will later edit it, and golden tests pin the two worlds together so they cannot drift. This is also the answer to whether the representation differs between frontend and backend: the CRDT bytes are identical everywhere, and what differs is altitude, with the client lifting the Loro document into a live EditorState, the server treating it as opaque mergeable bytes, and anything backend-side that needs meaning asking headless Lexical rather than growing a second brain.

Export is real markdown, in two dialects produced by the same transformer pipeline. The internal dialect round-trips losslessly, with Macro-specific constructs serialized as XML-ish tags carrying JSON payloads, so a user mention is `<m-user-mention>{"userId":…}</m-user-mention>` in the text. The external dialect is plain GitHub-flavored markdown in which mentions degrade to readable text and Macro-specific constructs flatten. You can take your documents to Obsidian or anywhere else, with the caveat that a third-party editor sees the external dialect, so the export is an exit ramp and an interchange format rather than a live sync target.

## what lives in the document

A document system faces one recurring question, which is whether a given piece of state belongs inside the collaborative document or adjacent to it, and our rule after two years is that state goes in the CRDT if and only if it must move atomically with the text under concurrent editing. Mentions are inside, as custom Lexical nodes serialized into the document, because they sit in the text flow, travel with cuts and pastes, and must merge like text; but a mention stores only the reference, and names, avatars, hover previews, and the backlink graph resolve live from services outside the document, so renaming a document updates every place it was ever mentioned. Property values are outside. Macro has a typed property system, strings, numbers, dates, selects, and entity references, shared by documents, tasks, emails, and CRM records, and a task's status has to be queryable across thousands of documents without opening a single CRDT, and writable by automations that hold no editor session; what lives inside the document is only the presentation state, the list of property IDs pinned to render under the title, stored on the root node alongside document metadata. Comments split the same way, with anchors inside the CRDT, because an anchor must survive concurrent edits to the text it points at, and thread content, resolution state, and notifications in ordinary backend services.

This boundary has been one of the higher-leverage decisions in the system. Each time we have been tempted to put queryable state into the document because it was conveniently at hand, we have regretted it, and each time we have held the CRDT to things that merge like text, the layer that is capable of losing people's words has stayed boring.

## dogfooding

We have run the company on Macro for two years, and the editor took the brunt of it, since every spec, meeting note, task description, and agent instruction the company produces goes through this code. <guess>Both of the bugs described above were found by us, on our own work, before customers hit them at any meaningful scale, and the disconnect bug in particular was kept honest by dogfooding, since every premature declaration of victory was falsified within days by somebody's laptop doing what laptops do.</guess>

The distinction that matters is between living in the product and playing with it, because twenty minutes of demo driving exercises the happy path, while living in it exercises the grim residue: laptops sleeping mid-sentence, hotel wifi, a document left open in a background tab for nine days, two people pasting into the same table during a call, a forty-page spec carrying three hundred mentions. <guess>Almost none of our worst bugs were reachable from casual use; they needed hours-long sessions and real stakes. Had we not been running the company on it, our estimate is that reaching the current quality bar would have taken two or three times as long, or, worse, we would have shipped at demo-quality and discovered the difference through churned customers rather than irritated colleagues. Dogfooding also reorders priorities in a way no process replicates, because when the CEO loses a paragraph the fix does not visit a backlog.</guess>

## results

What stands today is one sync layer under many surfaces. Documents, canvas, and PDF markup all multiplayer through the same Durable Object service; task descriptions and agent instructions are the same editor; offline editing queues locally and merges on reconnect through the identical code path as reconnection, which is why we trust it; and version history supports forking a document at a historical version through a server-side copy endpoint that operates on CRDT version vectors rather than a parallel revisions system. Search and AI read the same truth the editor writes, with re-indexing triggered by the last peer disconnecting and agents reading documents through the headless endpoints. <guess>Latency between keystroke and remote peer is one WebSocket hop through a Durable Object placed near the document's first users, tens of milliseconds in-region; documents into the hundreds of pages remain editable, with our worst real document around a 2 MB snapshot loading in under a second; and the claim we can make with a straight face is flawless at team scale, meaning tens of concurrent editors, and unproven at internet scale, because we have never needed a hundred cursors in one document.</guess>

<guess>Whether off-the-shelf would have been better depends on what you count. Liveblocks or a hosted tiptap backend would have produced a multiplayer demo months sooner, and pretending otherwise would be revisionism. The demo is not the product, though, and the properties that make the editor worth having, one schema across documents and tasks and agents, server-side parity through a headless parser, permissions enforced per-message inside our own auth system, are the properties that do not come off a shelf, so the months saved would have been spent building bridges to someone else's abstractions and paying per-seat for the privilege.</guess>

People ask what this would cost on AWS, since the stack is Cloudflare for sync and AWS for everything else. The equivalent architecture self-hosted looks like WebSocket termination on an ALB or API Gateway, a stateful room tier on Fargate with sticky sessions or Lambda with DynamoDB holding operation logs, ElastiCache for presence, and S3 for snapshots. <guess>At our scale, on the order of ten thousand documents touched per day with sessions averaging twenty minutes and low single-digit concurrent editors per active document, the Cloudflare bill for the sync tier lands in the low hundreds of dollars a month, dominated by Durable Object request and duration pricing with KV, R2, and D1 amounting to pennies, while the AWS sketch prices out between $1,500 and $3,000 a month before any cleverness, between always-on room capacity, load balancer and NAT fixed costs, and DynamoDB write units, and that figure excludes the cost that matters, which is that the room tier becomes a fleet you operate, with failover, draining stateful rooms on deploy, and rebalancing hot shards as your problems instead of Cloudflare's. The dollar gap is perhaps five to ten times; the operational gap is the actual reason we would choose Durable Objects again, with the fair caveat that DO pricing punishes chatty long-lived connections at much larger scale and we redo this arithmetic at every order of magnitude.</guess>

Against the incumbents the comparison is narrower than marketing would like. Google Docs remains better at being a pure document editor, with suggesting mode and a decade of operational-transform hardening we will not pretend to match. Obsidian wins local-first purism, since a vault is just files on disk, where our offline story is a CRDT cache and not a folder you can grep. Notion has breadth of database views we have not built. The bet is different in kind rather than degree: a document that can mention a task assigned from an email thread, with an agent reading all three under the same permission system, is worth more to a working team than any single surface's tenth year of polish, and unlike all three of those products, every line of how your words are stored is published.

## working with loro

Betting a core system on a young open-source CRDT taught us a few things worth passing on. The first is that you will read the source like it is yours, because operationally it is: we hit a real loro-crdt bug in which `EphemeralStore.subscribe` breaks under recursive aliasing, and our workaround, a `queueMicrotask` deferral behind an apologetic HACK comment in `core/collab/awareness.ts`, shipped the same day we found it, which is an afternoon's turnaround that no proprietary sync SDK's support queue would have matched. The second is that forks are loans rather than purchases. Our `js/loro-mirror` is a vendored fork of [loro-dev/loro-mirror](https://github.com/loro-dev/loro-mirror) taken from an earlier version and modified, and the license file in our tree documents its own exit plan, stating that we are planning on removing it and using the latest upstream directly; the fork was correct at the time, because we needed diffing behavior upstream did not yet have, and it accrues interest monthly in the form of upstream fixes we miss. The third is that running the same implementation on both ends of the wire is an underrated property: Loro being Rust-first means the identical CRDT merges your edits in the browser and in the Durable Object, and the entire category of client and server disagreeing about a merge does not exist for us.

<guess>The fourth lesson is about collaboration with maintainers. We talked with the Loro team about building the editor-binding layer together, roughly co-developing loro-mirror toward what a production block editor needs with us as the proving ground, and everyone was friendly, calls were had, and nothing shipped: we needed specific behaviors on a startup's deadline, they correctly declined to rush them into a public API they would support forever, we forked, the moment passed, and upstream later evolved in a different direction. There is no villain in that story, only the standard physics of a company's clock against a library's, and the conclusion is not to avoid collaborating but to keep collaborations off your critical path.</guess>

## what's next

<guess>The editor and sync surface has never had more than three engineers on it at once, and for long stretches it was closer to one and a half.
